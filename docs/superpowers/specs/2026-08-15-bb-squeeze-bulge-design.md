## 1. 決めたこと（前提）

- 新しいボリンジャーバンド（**5分足・20本・±2σ**）は **既存の 14本/0.7σ とは別系列**として足す。
  既存σは バンドウォーク判定と AI 文脈・プロンプト文言が共有しているため、触ると

## 2. 指標（①）

### 2.1 定数

`core/indicatorSpec.ts` に、既存 `BB_SIGMA` と**並べて**置く（見比べられる場所に置くのが目的）。

| 名前 | 値 | 用途 |
|---|---|---|
| `SQUEEZE_BB_PERIOD` | 20 | 新バンドの本数 |
| `SQUEEZE_BB_SIGMA` | 2 | 新バンドのσ |
| `SQUEEZE_BW_LOOKBACK` | 125 | BWhigh/low の参照本数 |
| `BB_SIGMA`（既存） | 0.7 | バンドウォーク判定・AI 文脈（**変更しない**） |

### 2.2 計算（純関数・`server/indicators.ts`）

確定した5分足の終値のみを使う。

- `bandwidth(upper, mid, lower)` = `(upper − lower) / mid × 100`。`mid<=0` / 未算出は `null`。
- `percentB(price, upper, lower)`（既存）= `(price − lower) / (upper − lower)`。幅0は `null`。
- `bandwidthExtremes(bwSeries, lookback)` = **現在足を含む**直近 `lookback` 本の最大 / 最小。
  本数が足りない間は「その時点までの最大/最小」を返し、`ready:false` を添える。
  ★`ready` は **非 null の BW の本数**で数える(枠の本数ではない)。BW は先頭 19本
  (=`SQUEEZE_BB_PERIOD − 1`)が必ず null なので、枠で数えると中身が足りないのに「参照本数ぶんの最小」を名乗る。
  → `ready:true` になるのは確定5分足が **91本(=参照72本+19)** 以上そろってから。
  ★実測(NIY=F 5分足 38,624本): 125本窓の実時間は **中央 13.1h / p95 61.1h / 最大 150h(6.2日)**。
  休憩帯(15:45-17:00 / 06:00-08:45)に足が無いため 10.4h にはならず、**窓の10.3%は48時間超**
  (=週末をまたぐ)。仕様として許容するが、「10.4時間」という当初の記述は誤りだった。
- `squeezeState(bw, high, low)` … `high === low`(窓内の BW が全部同値)のときは **判定しない(null)**。
  価格フィードが凍ると BW が一定になり、`bw <= low` が常に成立して永久にスクイーズへ張り付くため。

**足の窓(`server/loops/indicatorsLoop.ts`)**: スクイーズ用の足は既存の6時間窓とは **別に7日窓で取り直す**。
6時間窓では5分足が最大72本しかできず `ready` が永久に false(=判定が構造的に死ぬ)。一方で既存窓を
広げると `computeIndicators` の RSI が prefix 全体の Wilder 平滑化で **既存値そのものが変わる**
(バンドウォーク判定と AI プロンプトが共有する系列)ので、広げずに別窓を足す。
7日 = 上の実測の最大 150.1h(6.25日)を確実に含む幅(全期間 38,500窓のうち 168h 超は 0.000%)。
15秒 tick ごとに読み直さないよう、**確定足の終端時刻が前回と同じなら再計算しない**(実質5分に1回)。

### 2.3 画面（`web/components/indicatorPanel.ts`）

列数は変えず中身を差し替える。

```
RSI    %B     BW     BWhigh/low
52     0.83   1.42   2.10/0.61
```

- `%B` と `BW` は **1本前と比較**して 増加=緑 / 減少=橙 / 同値=灰。
- 値が出せない間（本数不足）は従来どおり `--` と不足本数を出す。

## 3. 状態の定義（②）

確定足ごとに判定する。

- **スクイーズ** … `BW <= BWlow`
- **バルジ** … `BW >= BWhigh`

BWhigh/low は現在足を含むので、これは「125本の新記録に達した足」を意味する（ボリンジャー本人の
定義に合わせる）。どちらでもない足は `null`。

## 4. アラート（③）

- 検知種別 `squeeze` / `bulge` を `core/detectionKinds.ts` に追加。
- **その状態に入った足で1回だけ**発火する（同じ状態が続く間は再発火しない）。
- 載せる値: 価格（確定足の終値）、`bandwidth`、`bwHigh`、`bwLow`。
- 出荷前に `npx tsx scripts/alert-audit.mts` で **実データの発火頻度**を確認する（検知を足す時の決まり）。

### 5.2 スクイーズ = 両側逆指値（⑤前半）

- 買い: スクイーズ足の**高値 + 5円**に逆指値。売り: **安値 − 5円**に逆指値。

  - 安全上限超 → **そのレッグは出さない**（既存 enforce と同じ「超えたら落とす」）
- 片方が約定したら**反対側は取り消す**（OCO）。

**前の安値は、そこから15円ずれたただの価格と統計的に区別できない。**

「裁量でダブルを見つけると勝率が高い」という体感は**後知恵**で説明がつく。前の安値まで戻る局面のうち
約半分はそもそも戻らず（ネック上抜けで消える）、戻った中の **68〜91% は安値を割って「ダブル」と呼ばれない**。
名前が付いた 9〜32% の中では確かに 48〜65% が測定移動まで伸びる。**名前が付く時点で勝負の前半が終わっている。**

第3弾（第5章の売買）は**スクイーズ/バルジのみ**とする。詳細は memory `project-double-pattern-backtest`。

なお `DOUBLE_BW_PEAK_RATIO` を 0.9 → **0.5** に緩めたのは、用途がアラート専用に確定して評価軸が
「損益」から「使える頻度で出るか」に変わったため（0.9 は7か月で相異なるW 2件・トップは0件＝検知として死んでいた）。

## 10. スクイーズ/バルジ後の上抜け・下抜け（v0.9.82・売買の代替）

売買を撤回した代わりに、**同じ観測をアラートとして出す**。判断はユーザーが行う。

| 種別 | 発火条件 |
|---|---|
| `squeeze_break`（上/下） | スクイーズが鳴った**確定5分足**の 高値+5円 を超えた / 安値−5円 を割った |
| `bulge_break`（上/下） | バルジが鳴った確定5分足で同様 |

- 緩衝 **5円**（呼値。既存の「節目ちょうどには置かない」流儀）
- 有効期限 **60分**（ユーザー指定）
- 重複は **1事象につき上下それぞれ1回**（往復したら両方鳴る＝それが情報）
- 新しいスクイーズ/バルジが鳴ったら前の水準は捨てる
- **方向を持つ**（`directional: true`）。親のスクイーズ/バルジは `directional: false` のまま

実データ（72時間）: `squeeze_break` 23件 / `bulge_break` 11件。180日窓では計 6.3件/日。
否定対照: 期限を外すと +13.0% / 緩衝を0円にすると +2.7%（**緩衝は絞りのノブとしてはほぼ効かない**）。
