# BB スクイーズ/バルジ — 指標・アラート・売買・ダブル再定義

作成 2026-08-15 / 対象 monitor（実取引は trade2 が追従）

## 1. 決めたこと（前提）

- 新しいボリンジャーバンド（**5分足・20本・±2σ**）は **既存の 14本/0.7σ とは別系列**として足す。
  既存σは バンドウォーク判定と AI 文脈・プロンプト文言が共有しているため、触ると
  **実走中の質問文 A/B（v1 vs v2）の標本が割れる**。新系列なら実験は無傷。
- ダブルの定義変更により、**過去の的中率記録は不連続になる**（ユーザー了承済み）。
- 売買規則（第5章）は **設定トグルで既定 OFF**。実取引がいきなり新しい入り方を始めないため。

## 2. 指標（①）

### 2.1 定数

`core/indicatorSpec.ts` に、既存 `BB_SIGMA` と**並べて**置く（見比べられる場所に置くのが目的）。

| 名前 | 値 | 用途 |
|---|---|---|
| `SQUEEZE_BB_PERIOD` | 20 | 新バンドの本数 |
| `SQUEEZE_BB_SIGMA` | 2 | 新バンドのσ |
| `SQUEEZE_BW_LOOKBACK` | 125 | BWhigh/low の参照本数 |
| `BB_SIGMA`（既存） | 0.7 | バンドウォーク判定・AI 文脈（**変更しない**） |

### 2.2 計算（純関数・`server/indicators.ts`）

確定した5分足の終値のみを使う。

- `bandwidth(upper, mid, lower)` = `(upper − lower) / mid × 100`。`mid<=0` / 未算出は `null`。
- `percentB(price, upper, lower)`（既存）= `(price − lower) / (upper − lower)`。幅0は `null`。
- `bandwidthExtremes(bwSeries, lookback)` = **現在足を含む**直近 `lookback` 本の最大 / 最小。
  本数が足りない間は「その時点までの最大/最小」を返し、`ready:false` を添える。
  ★125本 ≒ 10.4時間なのでセッションをまたぐ（月曜朝の窓は金曜夜を含む）。仕様として許容。

### 2.3 画面（`web/components/indicatorPanel.ts`）

列数は変えず中身を差し替える。

```
RSI    %B     BW     BWhigh/low
52     0.83   1.42   2.10/0.61
```

- `%B` と `BW` は **1本前と比較**して 増加=緑 / 減少=橙 / 同値=灰。
- 値が出せない間（本数不足）は従来どおり `--` と不足本数を出す。

## 3. 状態の定義（②）

確定足ごとに判定する。

- **スクイーズ** … `BW <= BWlow`
- **バルジ** … `BW >= BWhigh`

BWhigh/low は現在足を含むので、これは「125本の新記録に達した足」を意味する（ボリンジャー本人の
定義に合わせる）。どちらでもない足は `null`。

## 4. アラート（③）

- 検知種別 `squeeze` / `bulge` を `core/detectionKinds.ts` に追加。
- **その状態に入った足で1回だけ**発火する（同じ状態が続く間は再発火しない）。
- 載せる値: 価格（確定足の終値）、`bandwidth`、`bwHigh`、`bwLow`。
- 出荷前に `npx tsx scripts/alert-audit.mts` で **実データの発火頻度**を確認する（検知を足す時の決まり）。

## 5. 売買（④⑤）

monitor のシグナルエンジンに実装する（trade2 は monitor のシグナルを追従するので実取引にも効く）。
**設定トグル `squeezeTradeEnabled`（既定 false）** が OFF の間は、判定もアラートも出るが発注はしない。

### 5.0 ★規則発の入口を新設する（この章の前提・2026-08-15 追記）

現状、建玉に至る道は **AI を通る1本だけ**である（コードで確認済み）。

```
scalp-plan で AI に問う → AiPlan → planToArmed() → 武装 → 約定 → 建玉
```

ドテンも同じで、保有中の建玉を `heldPosition` としてプロンプトへ注入し、**AI が反転を返したときだけ**
`reverseToDoten()` が走る。ダブル（W ボトム）は**アラート止まり**で、発注へは繋がっていない。

本章の⑤⑥は「条件が満たされたら必ずこう出す」という決定的な規則であり、AI の判断を挟む余地が無い。
よって **AI を経由しない第2の入口**を足す。

- `ruleToArmed(source, direction, entry, stopWidth, ...)` … 検知の結果から `planToArmed` と
  **同じ形の武装**を作る純関数。AI の応答時間（数秒〜数十秒）と失敗（429/400）に依存しない。
- ドテンは `reverseToDoten()` の中身を再利用し、**AI の返事を待たない**版を用意する。
- ★**記録に発生源を必ず残す**: 武装・建玉・トレードに `source: 'ai' | 'rule:squeeze' | 'rule:double' | 'rule:doten'`
  を持たせる。入口が2つになるので、後から「どちらが建てたか」を分けて集計できないと
  成績の比較が不能になる（この案件で繰り返し起きた失敗の形）。
- trade2 は `signalId` と FILLED を追うだけなので、**変更不要のはず**（第1弾の実装後に実機で確認する）。

★プロンプトには何も足さない。**実走中の質問文 A/B を割らないため**（AI に伝えて判断させる案は、
この理由と「規則どおりに出る保証が無い」ことから採らない）。

### 5.1 バルジ = 利が乗っている建玉だけ強制決済（④）

- バルジの足で建玉があり、**評価損益が正**なら即決済する。
- 含み損（0 を含む）は**何もしない**。ロスカットに任せる。

### 5.2 スクイーズ = 両側逆指値（⑤前半）

建玉が無いときだけ。

- 買い: スクイーズ足の**高値 + 5円**に逆指値。売り: **安値 − 5円**に逆指値。
  （既存の「節目ちょうどには置かない」流儀に合わせる。緩衝は定数）
- 損切りは**反対側の足の価格**（買いなら安値−5円）。その幅が
  - 下限（既定55円）未満 → **下限まで広げる**
  - 安全上限超 → **そのレッグは出さない**（既存 enforce と同じ「超えたら落とす」）
- 片方が約定したら**反対側は取り消す**（OCO）。

### 5.3 ドテン（⑤後半）

- 建玉を持っている間にバルジが出たら、その**バルジ足の価格 P を建玉に記録**する
  （複数回出たら**直近の P** で上書き）。
- その建玉が**ロスカットで決済**されたとき、`entryPrice` と `exitPrice` が **P の反対側**にあれば
  反対方向へ即エントリー（ドテン）。同じ側なら何もしない。**ちょうど P** はまたいでいないので何もしない。

| 建玉 | エントリー | P | ロスカット | ドテン |
|---|---|---|---|---|
| 買い | 110 | 105 | 100 | する |
| 買い | 110 | 105 | 106 | しない |
| 売り | 100 | 105 | 108 | しない |
| 売り | 100 | 105 | 110 | する |

- ドテンのエントリーは成行相当（現在値）、損切り幅は既存の既定規律。

## 6. ダブルの再定義（⑥）

`server/swingDouble.ts` の条件を差し替える（**種別名は据え置き**＝画面と履歴の種別は変えない）。

ダブルボトム:

1. 右谷の安値が**バンドの内側**（`%B > 0` ＝ 下限バンドより上）
2. **左谷の %B ＜ 右谷の %B**
3. **左谷の足の BW が、その時点の BWhigh の 90%以上**（＝ピーク付近。`0.9` は定数）
4. エントリー: **ネック**（左谷と右谷の間の戻り高値）へ逆指値

ダブルトップは上下対称（右山の高値が `%B < 1`、左山の %B ＞ 右山の %B、ネック＝間の押し安値）。

## 7. 出す順番

| 版 | 中身 | 理由 |
|---|---|---|
| 1 | 第2〜4章（指標・パネル・アラート） | 売買に触らない。実データで発火頻度を見る |
| 2 | 第6章（ダブル再定義） | 検知の意味が変わるので単独で出す |
| 3 | 第5章（売買） | 実取引が動く。1 の実測を見てから緩衝幅を決める |

## 8. テストと実証

- 純関数（bandwidth / extremes / squeeze 判定 / ドテンの境界規則 / ダブルの新条件）は**表で固定**する。
  特にドテンは第5.3章の4行をそのままテストにする。
- 画面は `web/components/indicatorPanel.ts` を**実際に描画**して、値と色（緑/橙/灰）を検査する。
- アラートは `alert-audit` の実データ発火頻度を出荷条件にする。
- 否定対照: 旧実装に差し替えると新テストが赤になることを `git show HEAD:<path>` で確かめる。

## 9. リスクと非対象

- **実験への影響なし**: 既存 `BB_SIGMA` とプロンプト文言は1文字も変えない。
- **記録の不連続**: ダブルの的中率は定義変更の前後で比較できなくなる（了承済み）。
- **非対象**: 決済ロジック（phase-exit）そのもの、AI のエントリー判断、trade2 側のコード
  （monitor のシグナルを追従するだけなので変更不要のはず。1 の実装後に実機で確認する）。
